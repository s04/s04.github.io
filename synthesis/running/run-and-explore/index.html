Run and explore

synth run and synth explore are the two commands that test your system. This page explains when to use each, what they leave on disk, what their exit codes mean, and how to stop a run or run several side by side.

run versus explore

Section titled “run versus explore”
synth run synth explore
Timelines One, named t000. Many, named t000, t001, and so on.
Fault plans Drawn from the seed, or fixed with --plan. Fresh seeds, or mutations of earlier plans that reached new coverage.
Stops When the timeline ends. After --timelines or --budget, whichever comes first.
Use it to Try a change, run a scenario, debug one seed. Search for bugs; the mode for CI.

Both commands accept:

Flag Default Meaning
-c synthesis.yaml Config file. SYNTH_CONFIG or SYNTHESIS_CONFIG set it when -c is absent.
--seed random Root seed: a number, or any string, which is hashed.
--duration from config Length of each timeline’s driver phase.
--out out Artifact directory.
--json off Print the report as JSON instead of Markdown.

explore adds:

Flag Default Meaning
--timelines 5 Number of timelines. 0 runs until --budget.
--budget none Wall-clock limit, such as 30m. The timeline in progress finishes.
--corpus none Corpus file to load before and save after the run.
--mutate 0.5 Probability that a timeline mutates a corpus plan instead of using a fresh seed.

Every flag is listed in CLI.

Seeds

Section titled “Seeds”

The root seed determines every timeline’s seed, and each timeline’s seed determines its template, fault plan, driver choices, command seeds and ending. Run the same command with the same seed against the same cluster and synth makes the same decisions. The system’s behavior still varies with timing; see Replay, shrink and causality.

The corpus

Section titled “The corpus”

Exploring with fresh seeds alone samples the same kinds of schedule over and over. synth explore also learns from what it has seen:

  1. After each timeline, synth compares the timeline’s coverage features with every feature seen so far in this run and in the loaded corpus.
  2. If the timeline produced at least one new feature and finished cleanly, its plan joins the corpus.
  3. Each later timeline, with probability --mutate, takes a random corpus plan instead of a fresh draw and changes its fault schedule in one way: drop a fault, add one, shift one in time, stretch its duration, retarget it, or splice the schedule with a second corpus plan at a random cut. The result is re-checked against the overlap rules.

A mutated timeline keeps its parent’s template and swarm settings, gets a new seed for its commands, and has its targets mapped onto the current pods. The report shows the lineage, for example t007 (shift of t002).

Keeping the corpus between runs

Section titled “Keeping the corpus between runs”

Without --corpus, the corpus lives only for one run. With it, synth loads the file at the start (a missing file is an empty corpus) and writes it back at the end, keeping the 200 entries with the most features. Point every run of a project at the same file and each one starts where the last stopped. In CI, persist the file between jobs; see GitHub Actions.

A corpus is tied to a configuration: plans name its fault kinds, nodes and pods. Keep one corpus per configuration file.

Output

Section titled “Output”

Each run writes to <out>/<run-id>/, where the run ID combines the UTC time, the mode and the seed, such as 20261016-091502-explore-48213. <out>/latest is a symlink to the newest run.

The Markdown report goes to stdout, progress to stderr. --json replaces the Markdown on stdout with the content of report.json, for scripts:

The report explains each file.

Exit codes

Section titled “Exit codes”
Code Meaning
0 No findings.
1 At least one finding.
2 Harness or usage error: a bad flag or config, or every timeline failed before testing anything.
130 Interrupted. After the first Ctrl-C: healed and reported, no findings. After a second Ctrl-C: exited at once without healing.

Findings take precedence: an interrupted run that found something exits 1. A run where some timelines hit harness errors and the rest found nothing exits 0; the report’s headline says how many timelines ran.

Interrupting a run

Section titled “Interrupting a run”

Press Ctrl-C once to stop cleanly. synth:

  1. Stops launching commands and cancels the faults that have not started.
  2. Heals every fault on the cluster, under its own ten-minute timeout.
  3. Collects the timeline’s artifacts and writes the report.

The interrupted timeline is marked interrupted: its artifacts are complete up to the interrupt, but its assertions and default properties are not evaluated, since a cut-off run would report false failures. explore starts no further timelines. synth then exits 130, or 1 if a timeline that finished before the interrupt has findings. If every timeline was interrupted, the headline reads “Nothing tested” rather than “No findings”. A timeline interrupted before its driver phase (during deploy, setup or planning) injected no fault; it is marked interrupted the same way.

Note

synth heal undoes everything synthesis can leave behind: it resumes paused pod processes, removes pod network rules, deletes clock skews, then unpauses and restarts node containers, lifts CPU caps and removes node network rules. Every new timeline also heals leftovers and redeploys your namespaces before it starts.

Several clusters on one host

Section titled “Several clusters on one host”

Each cluster needs its own name, Docker network and host mount directory. Set them per shell with environment variables:

Variable Overrides Notes
SYNTH_CLUSTER cluster.name 1 to 32 lowercase letters, digits and -.
SYNTH_SUBNET cluster.subnet A CIDR. If it overlaps an existing Docker network, synth up picks the next free /16 and logs it.
SYNTH_MOUNT cluster.mount Absolute host path mounted into every node.

synth writes a private kubeconfig per cluster and never switches your current kubectl context, so parallel runs do not drive each other’s clusters. Inside a Buildkite job, the cluster name and subnet default to values derived from the job ID; see Buildkite.

Two systems can also share one cluster: synth discovers templates and fault targets only in the namespaces each configuration’s manifests create.

Resource needs

Section titled “Resource needs”

The default cluster has one server and three agents. Plan for about 4 GB of free memory and two or more CPU cores per cluster, plus whatever your system needs. On a laptop, run at most two clusters at once.

Timelines are slow compared with unit tests: setup, the first_ command, the driver phase (duration, default 90 s), healing, quiescence and the ending add up to a few minutes each. Heavy load from other processes on the host slows every phase and can turn timeouts into false findings, so check the load before long runs.

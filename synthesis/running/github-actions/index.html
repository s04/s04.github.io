GitHub Actions

synthesis ships a composite action that sets up a GitHub-hosted runner, creates a k3d cluster, runs synth explore and tears the cluster down. This page shows how to call it on demand, what it gives back, and how to control its runner budget.

Run beside CI, not as a gate

Section titled “Run beside CI, not as a gate”

Chaos runs are slow and their results are statistical: a timeline that finds nothing today proves little, and a bug that needs a rare fault combination may take hours of timelines to surface. Keep them out of the pull request path:

  • Run your unit and integration tests on every pull request, as usual.
  • Run synth on demand against your main branch: choose a short smoke run or a longer exploration when you need it.
  • Treat a finding as a bug report to triage, with a seed and a plan you can replay locally, rather than a red check that blocks a merge.

Quick start

Section titled “Quick start”

The action needs a Linux runner with Docker and sudo, which ubuntu-24.04 provides. It does not upload artifacts itself: add the upload-artifact step so you can download the report and the plans.

Tip

Pin the action to a release tag such as s04/synthesis@v0.1.0, or to a commit SHA, rather than @main. The action builds synth from its own source, so the pin decides which version of synth you run.

What the action does

Section titled “What the action does”
  1. Installs Go with the version from synthesis’ go.mod.
  2. Prepares the host: loads the sch_netem kernel module (installing linux-modules-extra if needed), since k3d nodes share the runner’s kernel and network faults need it, and raises the inotify limits.
  3. Installs k3d if the runner has none. It downloads k3d’s install.sh for the pinned version and checks its SHA-256 before running it.
  4. Builds synth and puts it on PATH.
  5. Restores the corpus from the Actions cache, if corpus is set.
  6. Runs synth up, then synth explore with your inputs.
  7. Runs synth down, even when exploration failed.

Third-party actions inside it (actions/setup-go, actions/cache) are pinned to commit SHAs, and inputs reach the shell through environment variables, never by interpolation into the script.

Inputs

Section titled “Inputs”
Input Default Meaning
config synthesis.yaml Path to your configuration file.
timelines 3 Number of timelines. 0 runs until budget.
budget none Wall-clock budget, such as 20m.
seed run ID and attempt Root seed.
corpus .synthesis-corpus/corpus.json Corpus file kept in the Actions cache. An empty string disables it.
fail-on-findings true Fail the step when there are findings. Harness errors fail it either way.
k3d-version v5.9.0 k3d release to install when the runner has none.
k3d-install-sha256 checksum for v5.9.0 SHA-256 of k3d’s install.sh at that tag. Change both together.

Job summary

Section titled “Job summary”

When GITHUB_STEP_SUMMARY is set, every report-producing synth command appends its Markdown report to the job summary, so findings, properties and the timeline table appear on the run’s page without downloading anything. A report larger than GitHub’s 1 MiB limit is cut at a line boundary, with a pointer to the full report.md artifact.

Keep the corpus between runs

Section titled “Keep the corpus between runs”

With corpus set (the default), the action restores the most recent saved corpus for the branch, or for any branch if there is none, before exploring, and saves the updated corpus under a new cache key afterwards. Each run therefore starts from the plans that earlier runs found interesting. See Run and explore.

A corpus belongs to one configuration. If you run several configurations, give each its own corpus path, or disable the corpus for the extra ones.

Give each shard a distinct seed, or the shards repeat each other’s timelines. Each shard saves its own cache entry, and the next run’s shards restore the most recent one.

On-demand smoke and deep runs

Section titled “On-demand smoke and deep runs”

The repository’s own chaos.yml has only a manual workflow_dispatch trigger. Open Actions → chaos → Run workflow, select a mode and configuration, and start the run. Pushes and schedules do not start chaos exploration.

Mode Run
Smoke (default) One timeline, one shard. Checks that exploration runs and produces a report.
Deep --timelines 0 --budget 30m on two shards, growing the cached corpus.

The selected mode sets the shard count directly; there is no separate planning job. The config input lets you try another configuration, such as the clock-fault one, without editing the workflow.

You can also start a run with the GitHub CLI:

A smoke run costs about ten runner-minutes. Deep mode budgets 30 minutes of exploration per shard, plus setup and cleanup, so it uses roughly an hour of runner time across its two jobs.

The bundled example is buggy on purpose, so that workflow sets fail-on-findings: "false" and instead checks that deep runs find the planted bugs. In your own repository, keep fail-on-findings: true so a finding turns the run red and notifies you.

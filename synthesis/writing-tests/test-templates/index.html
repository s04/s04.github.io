Test templates

A test template is a directory of executables that together exercise your system: one command prepares it, others drive traffic, and a last one checks the result. This page explains the layout synth expects, what it runs when, and how to check a template before a real run.

synth uses the same layout and prefixes as Antithesis, so a template written for synthesis also works there. For the platform’s own description, see the Antithesis test composer reference.

Layout

Section titled “Layout”

Templates live in a workload pod, under /opt/antithesis/test/v1/. Each subdirectory is one template, and each executable inside it is one test command:

A command can be any executable: a shell script, a compiled binary, a Python file with a shebang. synth runs it with kubectl exec inside the container it was found in, so it sees that container’s filesystem, network and environment.

The workload pod

Section titled “The workload pod”

The workload pod is an ordinary pod in your manifests that holds the templates and stays idle so synth can exec into it:

  1. Build an image that contains your test commands under /opt/antithesis/test/v1/<template>/.
  2. Start it with a command that never exits, such as sleep infinity.
  3. Label it synthesis.dev/role: workload. synth discovers templates only in pods that match composer.workloadSelector (default synthesis.dev/role=workload) and live in the namespaces your manifests create.

Tip

Pin the workload pod to the server node, as above. The server node is never faulted, so your drivers keep running while the system under test is disrupted. See Manifests for the labels synth reads.

Command prefixes

Section titled “Command prefixes”

A command’s file name decides when it runs. synth recognizes seven prefixes:

Prefix When it runs
first_ Once, before any fault and before any driver. If a template has several, synth picks one.
parallel_driver_ Repeatedly during the driver phase, several at a time, up to the timeline’s parallelism.
serial_driver_ During the driver phase, alone: running parallel drivers finish first.
singleton_driver_ At most once per timeline; when chosen, no other driver runs on that timeline.
anytime_ Throughout the driver phase, alongside the drivers, while faults are active.
eventually_ After the drivers were killed and every fault was healed. Asks “does the system recover?”
finally_ After every driver finished on its own and every fault was healed. Asks “is the end state right?”

Files that start with helper_ are ignored, so you can keep scripts your commands share next to them. Every template needs at least one driver (parallel_driver_, serial_driver_ or singleton_driver_) or one anytime_ command; synth drops a template that has none and reports it.

What one timeline runs

Section titled “What one timeline runs”

A timeline is one deployment of your system under one seed. Its commands run in this order:

  1. synth deploys your manifests and waits for the setup gate.
  2. It discovers the templates and picks one: the one named in composer.template, or else one drawn from the seed.
  3. It runs one first_ command to completion. No faults are active yet. A first_ that fails is logged, and the timeline goes on.
  4. It draws the fault plan, starts the fault injector, and starts the driver phase, which lasts duration (default 90s). During it:
    • If the template has singleton_driver_ commands, synth runs one of them instead of the other drivers: always when there is no other driver, otherwise on about 30% of timelines.
    • Otherwise it keeps launching parallel_driver_ commands, up to this timeline’s parallelism (drawn between 1 and composer.maxParallel). On about one launch in ten it runs a serial_driver_ alone instead.
    • anytime_ commands run one after another at random intervals (about 4 s apart on average).
  5. When the phase ends, synth chooses the ending, stops the injector, heals every fault, waits for the workloads to be ready again, and waits quiescence (default 15s).
  6. It runs every command of the chosen ending, one at a time, in a seeded order.

How the ending is chosen

Section titled “How the ending is chosen”
Template has Ending
Only eventually_ eventually_: running drivers are killed when the phase ends.
Only finally_ finally_: synth waits up to composer.commandTimeout for running drivers to finish on their own.
Both One of the two, drawn from the seed with equal odds.
Neither No ending; the timeline only checks what the commands asserted along the way.

finally_ only runs when every started command ended by itself. If a driver is still running after the wait, synth kills it and falls back to eventually_ (or to no ending when the template has none). If a command was killed or timed out, the ending is skipped. The report’s timeline table shows which ending ran.

Environment of a command

Section titled “Environment of a command”

Every command gets these variables in addition to its container’s own environment:

Variable Meaning
SYNTHESIS_SEED A decimal 64-bit seed drawn for this command. Seed your command’s randomness from it so a replay makes the same choices.
SYNTHESIS_TIMELINE The timeline’s name, such as t003.
SYNTHESIS_COMMAND_ID The command’s run number within the timeline.
ANTITHESIS_OUTPUT_DIR A per-pod output directory that synth collects. Write logs, histories and artifacts there.
ANTITHESIS_SDK_LOCAL_OUTPUT Where the SDKs write assertions when they run in local-output mode.
ANTITHESIS_STOP_FAULTS A script that pauses fault injection. See Faults.
SYNTHESIS_FAULT A helper that requests a fault on demand. See Workload faults.

The ANTITHESIS_* and SYNTHESIS_FAULT variables are injected into every container of your manifests, not only the workload pod. The full list is in Environment variables.

Timeouts and exit codes

Section titled “Timeouts and exit codes”

Each command runs under composer.commandTimeout (default 5m). A command that exceeds it is killed inside the pod and recorded as timeout.

Exit 0 when the command ran, whatever it found. Report what you found with assertions, not with the exit code: a non-zero exit is itself a failure of the default property Commands finish with zero exit code, unless the command’s own pod or node was faulted while it ran. See Properties.

Invalid names

Section titled “Invalid names”

synth reports a file under a template directory as invalid when:

  • its name starts with none of the seven prefixes and not with helper_;
  • it is not executable;
  • it is a directory (unless it starts with helper_).

A template without a driver or anytime_ command is invalid as a whole. Invalid entries never run. Each timeline records them in the default property No invalid commands found, which the report shows as a warning: it points at a broken test setup, not at a bug in your system.

Worked example: the kv template

Section titled “Worked example: the kv template”

The bundled examples/kv ships its main template in test/main/. Each command is a two-line script that calls the kvwork binary:

File What it does
first_setup Waits for the three replicas to agree on a leader, then writes a few keys. Faults are off.
parallel_driver_ops Runs 15 to 30 random put, get and compare-and-set operations against random replicas, and appends each to a history file in $ANTITHESIS_OUTPUT_DIR.
anytime_health Polls every replica’s status while faults are active, and asserts whether they agree on a leader.
eventually_check After the drivers were killed: checks that replicas converge, no acknowledged write was lost, and the history is linearizable.
finally_check The same checks, after the drivers finished on their own.
helper_status.sh A debugging aid, ignored by synth.

kvwork seeds its choices from SYNTHESIS_SEED, exits 0 even when a check fails, and reports every verdict through the Go SDK. Because the template has both eventually_ and finally_, each timeline draws one of the two endings.

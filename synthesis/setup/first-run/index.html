First run

This page walks you through a complete session with the example that ships in the repository: a small replicated key-value store with bugs planted in it. By the end you will have found those bugs, reproduced one, and cut its fault schedule down to the essentials.

You need a checkout of the repository and a built synth (see Install). Run every command from the repository root: the synthesis.yaml there is the configuration for this example.

The system under test

Section titled “The system under test”

examples/kv is a three-replica, in-memory key-value store over HTTP. It behaves correctly as long as nothing fails. Under faults, it has realistic replication bugs:

Bug What triggers it
Stale reads from a leader that was paused and woke up still believing it leads pausing the leader during traffic
Writes acknowledged by the leader alone (sloppy quorum) pausing or partitioning followers
Split brain: two replicas both accept writes a partition that isolates the leader from its peers but not from clients
A returning leader overwrites followers that hold newer data pausing or partitioning the leader, writing, then healing
Lost writes when a replica restarts empty and leads at once restarting kv-0 while the other replicas are unreachable

The workload records a Jepsen-style history of every operation. Its eventually_ and finally_ commands check that the replicas converge, that no acknowledged write was lost, and that the history is linearizable (using Porcupine).

1. Create the cluster

Section titled “1. Create the cluster”

This creates a k3d cluster named synthesis with one server and three agents, installs synthesis’ helpers (a network-tools image and the synthesis-agent DaemonSet), builds libvoidstar.so for your node architecture, then builds the synthesis-kv:dev image and imports it into every node. The first time takes a few minutes; later runs reuse the cluster and the build caches.

Note

synth writes a private kubeconfig for the cluster and never switches your current kubectl context. To look around yourself, use k3d kubeconfig write synthesis and point KUBECONFIG at the file it prints.

Section titled “2. Validate the test setup”

synth deploys the example once and lists the test templates and commands it found in the workload pod:

It exits 0 when every template is valid. Exit 1 means a file name is invalid or no template was found, so fix that before going further. The example’s config forces the main template with composer.template: main.

3. Run one timeline

Section titled “3. Run one timeline”

A timeline takes a couple of minutes: deploy, setup, first_setup, a 60-second driver phase under faults, heal, 10 seconds of quiescence, then the ending. Progress goes to stderr, and the markdown report goes to stdout. Artifacts land in out/<run-id>/, and out/latest points at the newest run.

A single timeline may or may not hit a bug: it depends on which faults the seed drew. The exit status tells you: 0 means no findings, 1 means findings.

4. Explore

Section titled “4. Explore”

Now synth runs ten timelines, each with its own swarm of fault kinds, and mutates the schedules that reached new behaviour. On this example a run of this size reliably finds the planted bugs. Expect findings such as:

  • History is linearizable (stale reads, split brain);
  • Replica version never decreases (a returning leader rolls a follower back);
  • Acknowledged writes are not lost (lost writes on restart);
  • Replicas converge after faults stop.

Each finding lists the timelines it failed in and ready-made replay and shrink commands.

5. Read the report

Section titled “5. Read the report”

Open the HTML report:

It shows the findings first, then every property with its pass/fail counts, the default properties, code coverage per module, and for each timeline a swimlane of faults and commands over time. See The report for a tour.

6. Replay a failure

Section titled “6. Replay a failure”

Pick a failing timeline from the report, say t003, and replay it:

synth re-runs the same seed, fault schedule and command schedule three times and reports how often each original failure came back. Expect a rate rather than a yes or no: the cluster is real, so timing varies.

Caution

out/latest moves with every run, including replays. Copy the path of the plan you care about (or the whole run directory) before running the next command.

7. Shrink it

Section titled “7. Shrink it”

synth removes faults from the schedule, keeping only those needed for the property to still fail, and writes the result to out/<new-run-id>/shrunk-plan.json. On this example a typical schedule shrank from eight faults to two: partition kv-1 away, then kill kv-0’s node.

8. Find when it became inevitable

Section titled “8. Find when it became inevitable”

At four cut points, synth keeps the original faults before the cut, redraws the rest, and measures how often the property still fails. A low rate early and a high rate after some cut tells you the decisive events happened in between.

Variations

Section titled “Variations”

The example ships two more configurations:

  • examples/kv/synthesis-hegel.yaml drives the store with a Hegel state machine that requests faults itself and shrinks operations and faults together. See Hegel.
  • examples/kv/synthesis-clock.yaml enables only clock skips (amd64 hosts; installs Chaos Mesh during synth up).

Pass either with -c, for example synth run -c examples/kv/synthesis-hegel.yaml --seed 1. The Hegel configuration reuses the synthesis cluster; the clock configuration creates its own (syn-clk, subnet 172.45.0.0/16), so run synth up -c with it first.

Configuration

This page walks through synthesis.yaml, the one file that tells synth what to deploy, how to build the cluster and how hard to push. For a terse table of every field, see the configuration reference.

Where synth looks

Section titled “Where synth looks”

Every command that needs a configuration reads, in order:

  1. the file passed with -c FILE;
  2. $SYNTH_CONFIG, then $SYNTHESIS_CONFIG;
  3. synthesis.yaml in the current directory.

Relative paths inside the file (manifests, catalog, build, cluster.mount) are resolved against the directory that holds the file, not your working directory.

The full file, annotated

Section titled “The full file, annotated”

The values below are the defaults unless the comment says otherwise.

Swarm is off by default

faults.swarm defaults to false, which enables every listed kind on every timeline. Most projects want swarm: true for exploration; the bundled example sets it.

Choosing values

Section titled “Choosing values”

duration and quiescence. A timeline lasts roughly deploy + setup + duration + quiescence + the ending. Shorter driver phases mean more timelines per hour; longer ones let slow failure modes build up. Set quiescence to at least the time your system needs to notice a healed partition and converge.

faults.intensity. With the default 0.15, a 90-second driver phase sees about 13 fault arrivals before the overlap rules drop some. Raise it for systems that recover fast; lower it when every fault needs a long recovery. The swarm scales it by ½, 1 or 2 per timeline.

faults.maxNodeFaults. Keep it below the number of replicas your system can lose and still make progress. With three replicas, 1 is the honest setting; 2 tests availability under minority loss and quorum loss.

faults.enabled. all, node.* and pod.* never include the clock kinds. Name pod.clock or pod.clock_all explicitly; that also makes synth up install Chaos Mesh (needs helm, amd64 nodes). The kinds are listed in Fault kinds.

setup.requireSignal. Turn it on once your system calls the SDK’s setup-complete function. A timeline whose system never signals readiness is then a failed “Setup completed” property rather than a silent fallback.

Labels your pods need

Section titled “Labels your pods need”

synth finds your pods through two label selectors.

Label Put it on Effect
synthesis.dev/fault-target: "true" the pods of your system under test they become targets for pod.* faults (faults.podSelector)
synthesis.dev/role: workload the pod that holds your test templates test commands run in it (composer.workloadSelector)

The workload pod should keep running on its own, for example with command: ["sleep", "infinity"], and should be scheduled on server-0 so node faults never take it down. See Manifests.

The assertion catalog

Section titled “The assertion catalog”

Without an instrumentor, an assertion that never runs leaves no trace, so a Sometimes that was never reached looks the same as one that does not exist. List your source trees under catalog: and synth scans them for SDK assertion calls (Go, Python, Java and Kotlin, TypeScript and JavaScript, Rust, C and C++, and .NET spellings). Each call it finds is declared up front, so unreached ones show up in the report and must-hit ones (Sometimes, Reachable) fail when nothing reached them.

The scanner skips vendor, node_modules, .git, target and Go test files. The message must be a string literal, as the SDKs require. The Rust, C++ and .NET SDKs emit their own catalog, so they need no scan.

libvoidstar

Section titled “libvoidstar”

voidstar: true (the default) mounts synthesis’ libvoidstar.so at /usr/lib/libvoidstar.so in every container, plus a per-timeline seed file at /synthesis/seed. The official SDKs load it automatically. Set voidstar: false for a system that must not see it, for example one that ships its own library at that path. See libvoidstar.

Environment overrides

Section titled “Environment overrides”

These variables override the cluster placement without editing the file. They exist so that several runs can share one Docker host.

Variable Overrides Notes
SYNTH_CONFIG, SYNTHESIS_CONFIG the config path used when -c is not given; SYNTH_CONFIG wins
SYNTH_CLUSTER cluster.name 1–32 lowercase letters, digits and -
SYNTH_SUBNET cluster.subnet a CIDR; synth up still moves to a free /16 if it is taken
SYNTH_MOUNT cluster.mount must be an absolute path

Inside a Buildkite job, an unset SYNTH_CLUSTER or SYNTH_SUBNET is derived from BUILDKITE_JOB_ID. All variables are listed in Environment variables.

Note

The mount directory is fixed when the cluster is created. Later commands read it from the running cluster, so changing cluster.mount or SYNTH_MOUNT only takes effect after synth down and synth up.

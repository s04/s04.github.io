Manifests

This page explains how synth treats the manifests you list under manifests:: what it adds to them, which shapes it accepts, and what it deletes between timelines. Read it before you point synth at your own system.

What synth deploys

Section titled “What synth deploys”

synth applies your manifests as they are, after adding a small runtime contract to every pod template. It does not use Helm, Kustomize or an operator, and it does not install anything else into your namespaces.

The bundled examples/kv/manifests/kv.yaml is a complete example: a Namespace, a headless Service, a StatefulSet for the replicas and a Deployment for the workload pod.

Supported shapes

Section titled “Supported shapes”
  • Files and directories. Each entry under manifests: is a file or a directory. Directories are walked recursively for .yaml, .yml and .json files, read in sorted path order.
  • Multi-document YAML. Every ----separated document is read.
  • kind: List is flattened into its items, recursively.
  • Documents without kind or apiVersion, such as a kustomization.yaml in the same directory, are skipped with a warning.
  • Apply order. CustomResourceDefinitions are applied first and synth waits until they are established; then Namespaces; then everything else.
  • Pod templates. The contract is injected into Pod, Deployment, StatefulSet, DaemonSet, ReplicaSet, Job and CronJob objects. Other kinds are applied untouched.
  • Rollout. Before the setup gate, synth waits for every Deployment, StatefulSet and DaemonSet to finish rolling out, up to setup.timeout.

What synth injects into every pod

Section titled “What synth injects into every pod”

On each timeline, before applying, synth edits every pod template. Every container, including init containers, gets these environment variables:

Variable Value Purpose
ANTITHESIS_OUTPUT_DIR /synthesis/out where SDKs and your tools write output
ANTITHESIS_SDK_LOCAL_OUTPUT /synthesis/out/sdk.jsonl SDK JSONL fallback file
ANTITHESIS_STOP_FAULTS /synthesis/bin/antithesis-stop-faults script that pauses fault injection
SYNTHESIS_FAULT /synthesis/bin/synthesis-fault helper to request a fault now
SYNTHESIS_POD_NAME the pod’s name (downward API) per-pod output subdirectory

and these volumes:

Volume Mounted at Source on the node
synthesis-out /synthesis/out, with subPathExpr: $(SYNTHESIS_POD_NAME) /synthesis/runs/<run-id>/<timeline>/, so each pod writes into its own subdirectory
synthesis-bin /synthesis/bin (read-only) /synthesis/bin, the helper scripts

With voidstar: true (the default), every container also gets:

Addition Value
SYNTHESIS_VOIDSTAR 1
SYNTHESIS_SEED_FILE /synthesis/seed
file mount /usr/lib/libvoidstar.so (read-only) synthesis’ library, built for the node architecture
file mount /synthesis/seed (read-only) this timeline’s seed for long-running processes

/synthesis on each node is the host directory cluster.mount (default .synthesis/mnt next to your config), so everything pods write is visible to synth on the host. A volume, mount or variable that your manifest already defines under the same name or path is replaced in place.

Note

Test commands additionally receive SYNTHESIS_SEED, SYNTHESIS_TIMELINE and SYNTHESIS_COMMAND_ID when the composer starts them. They are not in the pod spec. See Environment variables.

Labels and placement

Section titled “Labels and placement”

Two labels connect your manifests to synth:

  • synthesis.dev/fault-target: "true" on the pod template of each component that pod faults may hit;
  • synthesis.dev/role: workload on the pod that holds /opt/antithesis/test/v1/ and runs your test commands.

Keep the workload pod alive on its own (command: ["sleep", "infinity"]) and pin it to the control-plane node, which is never faulted, so a node fault never kills your driver:

Spread your replicas across the agents (one replica per agent is the simplest), so node faults affect one replica at a time.

Namespaces and reset

Section titled “Namespaces and reset”

Each timeline starts from a clean slate on the same cluster:

  • Namespaces your manifests create or use (other than default and kube-system) are deleted with everything in them, and synth waits until they are gone. Pods stuck terminating, usually on a node that died, are force-deleted after three minutes.
  • Objects in default, or with no namespace, are deleted one by one, and synth waits for their pods to go.
  • Namespaces and CRDs listed in your manifests are applied again, not deleted individually.

Put your system in its own namespace. It makes reset fast and complete, and keeps it away from anything else on the cluster.

Tip

Discovery and fault targeting only look at the namespaces your manifests put pods in, so two systems with different namespaces can share one cluster. Point the second at the first with SYNTH_CLUSTER.

Images

Section titled “Images”

Images listed under images: are imported into every node with k3d image import; they are never pulled. Set imagePullPolicy: IfNotPresent (or Never) on containers that use them. Because an imported image cannot be pulled back, synth creates clusters with kubelet image garbage collection disabled, and before each timeline it re-imports any listed image a node has lost. Public images in your manifests are pulled as usual.

StatefulSets for replayable runs

Section titled “StatefulSets for replayable runs”

Prefer StatefulSets for the components you want to fault and replay:

  • Stable fault targets. Pod faults target pods by name. A StatefulSet’s kv-0, kv-1, kv-2 exist on every timeline, so a recorded plan and a shrunk plan still name real pods. Deployment pods get new random names each timeline. explore maps corpus plans onto the current pods by name stem, but replay, shrink, causality and run --plan reject a plan whose targets no longer exist.
  • Replayable randomness. libvoidstar gives a long-running process a random stream keyed by its command line and pod name. A stable pod name means the same stream on replay; a Deployment pod’s random name means a new stream every run.

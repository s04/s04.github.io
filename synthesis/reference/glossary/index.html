Glossary

This page defines the terms the rest of the documentation uses. Where a term comes from Antithesis, the definition here says what it means in synthesis; follow the link for the original concept.

Corpus

Section titled “Corpus”

The set of fault plans synth explore keeps because they reached new coverage: a new assertion outcome, a new hit-count bucket, a closer guided value, or a new code edge. New timelines either mutate a corpus plan or draw a fresh seed. Saved with --corpus FILE (at most 200 entries).

Default property

Section titled “Default property”

A property synth checks without any assertion from you: setup completed, no invalid commands found, commands finish with zero exit code, no unexpected container exits. Modelled on Antithesis’ default properties.

Driver

Section titled “Driver”

A test command that generates load during the driver phase: parallel_driver_, serial_driver_ or singleton_driver_. anytime_ commands run alongside them.

Ending

Section titled “Ending”

How a timeline finishes. With eventually_, the drivers are killed and the command checks recovery. With finally_, the drivers finish and the command checks the end state. Faults are healed and the cluster settles before either. Chosen by the seed among the endings the template has.

Expression

Section titled “Expression”

One distinct way a property failed. Failures of a property are grouped by the shape of their details; two expressions usually mean two code paths to the same broken expectation.

Finding

Section titled “Finding”

A failed property that the report lists at the top, with the timelines it failed in and commands to replay and shrink it. Any finding makes synth exit 1.

Incarnation

Section titled “Incarnation”

The restart count of one process within a timeline, as libvoidstar counts it. Each incarnation draws from its own random stream, and a replay’s k-th restart gets the same stream as the original’s k-th restart.

Nemesis

Section titled “Nemesis”

The part of synth that applies and reverts faults on schedule. The term comes from Jepsen.

Plan

Section titled “Plan”

Everything needed to repeat a timeline’s decisions: the seed, template, swarm, planned faults, workload-requested faults, recorded commands, ending and fault targets. Stored as plan.json in each timeline directory.

Property

Section titled “Property”

A named expectation, judged over all timelines of a run. SDK assertions with the same message form one property; default properties are added by synth.

Quiescence

Section titled “Quiescence”

The settle time (quiescence, default 15 s) after every fault is healed and before the ending’s commands run.

Swarm

Section titled “Swarm”

The per-timeline configuration drawn from the seed: which enabled fault kinds are on, the driver parallelism, and an intensity multiplier. From swarm testing.

Test template

Section titled “Test template”

A directory /opt/antithesis/test/v1/<name>/ in the workload pod whose executables, named by prefix, form one kind of test. See Test templates and Antithesis’ test composer reference.

Timeline

Section titled “Timeline”

One deployment of the system under test under one seeded fault schedule, from reset to ending. run executes one; explore many.

voidstar

Section titled “voidstar”

Short for libvoidstar.so, the native library the official SDKs load from /usr/lib/. synthesis ships its own; see libvoidstar.

Workload pod

Section titled “Workload pod”

The pod labelled synthesis.dev/role: workload that holds the test templates and in which synth runs every test command.

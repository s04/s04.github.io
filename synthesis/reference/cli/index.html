CLI

This page lists every synth command, its flags and their defaults. The same text is available offline: synth help prints the overview and synth help <command> (or synth <command> -h) prints one command’s usage.

Conventions

Section titled “Conventions”
  • Flag syntax. One-letter flags take one dash (-c, -o), longer ones two (--seed). The parser accepts either, and --flag=value or --flag value.
  • Flags anywhere. Flags may come before or after positional arguments. Everything after -- is positional.
  • Output streams. Commands that produce a report print the markdown report (or, with --json, the content of report.json) on stdout and progress on stderr, so synth run > report.md works.
  • Artifacts. Each run writes into <out>/<run-id>/ and points the symlink <out>/latest at it. A run id looks like 20261016-150405-explore-12345: UTC time, mode, and the seed modulo 100000.

Shared flags

Section titled “Shared flags”
Flag Default Meaning Taken by
-c FILE $SYNTH_CONFIG, else $SYNTHESIS_CONFIG, else synthesis.yaml configuration file every command except kinds and voidstar
--out DIR out artifact directory validate, run, explore, replay, shrink, causality
--seed SEED random root seed: a uint64, or any string (hashed to one) run, explore, plan
--duration DURATION the config’s duration driver phase per timeline, e.g. 30s run, explore, plan, replay, shrink, causality
--json off print the report as JSON instead of markdown run, explore, replay, shrink, causality

Exit codes

Section titled “Exit codes”
Code Meaning
0 No findings (or the command succeeded).
1 At least one finding. For validate: a test template is invalid or none was found.
2 Harness or usage error: bad flags, unreadable config, cluster or deploy failure, or every timeline failed with a harness error.
130 Interrupted. The first Ctrl-C (or SIGTERM) stops the run, heals the cluster, writes the report and exits 130 unless there are findings (then 1), even if some timelines finished before the interrupt. A second Ctrl-C exits 130 at once without healing; run synth heal afterwards.

Cluster commands

Section titled “Cluster commands”

synth up

Section titled “synth up”

Creates the k3d cluster the config describes (if it does not exist yet), writes its private kubeconfig, installs the network-tools helper image and the synthesis-agent DaemonSet, installs Chaos Mesh when a clock fault kind is enabled or faults.clock is set, builds and installs libvoidstar.so (unless voidstar: false), then runs every build: entry and imports the images: into the nodes. Safe to run again on an existing cluster.

If the configured subnet overlaps an existing Docker network, up picks a free /16 instead and says so.

synth down

Section titled “synth down”

Deletes the cluster. The mount directory on the host is kept.

synth clean

Section titled “synth clean”

Deletes the host mount directory, including files pods wrote there as root. Refuses while the cluster still exists: run synth down first.

synth build

Section titled “synth build”

Runs the build: entries and imports the images: into the existing cluster, without touching anything else. Use it after changing your code.

synth validate

Section titled “synth validate”

Deploys the system once and prints the test templates and commands it finds under /opt/antithesis/test/v1 in the workload pods, one line per command (type, name, namespace/pod), plus an INVALID line for each badly named file. Artifacts go to <out>/validate/.

Exit status: 0 every template is valid; 1 a template is invalid or none was found; 2 validate itself could not run.

synth heal

Section titled “synth heal”

Undoes every node-level fault, whatever synth believes it applied: unpauses paused node containers, starts stopped or killed ones, removes CPU limits, and clears synthesis’ tc and iptables rules in each node’s network namespace. It is idempotent and works after a crash.

Before the nodes, it heals pod-level faults in the namespaces of the configured manifests: it resumes paused pod processes, removes synthesis’ rules from pod network namespaces and deletes clock skews. If the manifests cannot be loaded, it heals the nodes only. Run synth heal after a second Ctrl-C, or whenever nodes or pods look stuck.

Tools

Section titled “Tools”

synth kinds

Section titled “synth kinds”

Prints the fault catalog: each kind with its Antithesis name, type, whether it is disruptive, and whether it is opt-in. Needs no config or cluster. See Fault kinds.

synth voidstar

Section titled “synth voidstar”
Flag Default Meaning
--arch the Docker daemon’s architecture amd64 or arm64
-o libvoidstar.so output path

Builds synthesis’ libvoidstar.so in Docker, for use outside a synth cluster (for example in your own images or tests). synth up and the first deploy of a run do this automatically for the cluster.

Timelines

Section titled “Timelines”

synth run

Section titled “synth run”

Runs one timeline named t000: deploy, drive the workload under a seeded fault schedule, check properties, heal, and write report.{md,html,json}.

Flag Default Meaning
--plan FILE none fixed fault schedule: a recorded plan.json or a hand-written scenario. The workload is fresh: its seed comes from --seed and its commands are not replayed.

synth explore

Section titled “synth explore”

Runs many timelines (t000, t001, …), keeps a corpus of plans that reached new assertion or code coverage, and mutates them. Stops after --timelines or --budget, whichever comes first.

Flag Default Meaning
--timelines 5 number of timelines; 0 means until --budget
--budget 0 (none) wall-clock budget, e.g. 30m
--corpus none (in memory) corpus file to load at start and save at the end (the 200 richest entries)
--mutate 0.5 probability of mutating a corpus plan instead of drawing a fresh seed

synth plan

Section titled “synth plan”

Prints, as JSON on stdout, the fault schedule synth run --seed SEED would use, and a one-line description of each fault on stderr. Nothing is deployed or injected, but the cluster must exist, because the planner needs its nodes and fault-target pods.

Replay and analysis

Section titled “Replay and analysis”

These commands take one positional argument, the path to a plan.json recorded by an earlier run (<out>/<run-id>/<timeline>/plan.json). When a result.json sits next to it, its failures are the “original failures”. Plans read from disk are validated before they drive Docker or kubectl: unknown kinds, targets that are not current nodes or pods, and non-finite or negative times are rejected.

synth replay

Section titled “synth replay”

Re-runs the timeline (same seed, fault schedule, command schedule and ending) --times times and reports how often each original failure reproduced. Timelines are named r000, r001, …

Flag Default Meaning
--times 3 number of replays (must be > 0)

synth shrink

Section titled “synth shrink”

Delta-debugs the fault schedule down to a minimal one that still fails the property, and writes it to <out>/<run-id>/shrunk-plan.json. Timelines are named s000, s001, …

Flag Default Meaning
--property the plan’s first original failure property (assertion message) to keep failing
--max-runs 20 maximum replays (must be > 0)

synth causality

Section titled “synth causality”

At --points cut points across the driver phase, keeps the plan’s history up to the cut, redraws what comes after, and measures the failure rate of the property over --times runs per point.

Flag Default Meaning
--property the plan’s first original failure property to measure
--points 4 cut points across the driver phase (must be > 0)
--times 3 runs per cut point (must be > 0)

shrink and causality exit 2 when the plan had no original failure and --property is not given.

Other

Section titled “Other”

synth help

Section titled “synth help”

Without an argument, prints the overview of all commands, the environment variables and the exit codes. With one, prints that command’s usage, flags, environment and exit status. -h, -help and --help work as aliases, both alone and after a command.

synth version

Section titled “synth version”

Prints synth <version> (<revision>, <go version>), for example synth v0.1.0 (1a2b3c4d5e6f, go1.26.6). A build from a modified checkout shows -dirty after the revision. --version and -version are aliases.

Environment

Section titled “Environment”

The variables every config-reading command honours (SYNTH_CONFIG, SYNTHESIS_CONFIG, SYNTH_CLUSTER, SYNTH_SUBNET, SYNTH_MOUNT) and the rest are listed in Environment variables.

Architecture

This page is for contributors and for anyone who needs to know exactly what synth does to a cluster. It maps the packages, follows one timeline through them, describes the boundary between the host and untrusted pods, and lists the development workflows.

Package map

Section titled “Package map”
Path Responsibility
cmd/synth The CLI: a command table (cmd_cluster.go, cmd_run.go, cmd_replay.go) built on urfave/cli v3, plus config loading and the run/finish steps shared by the timeline commands.
internal/clix synthesis’ own CLI glue around urfave/cli: exit-code errors, env fallbacks for flags, the compact help template, usage errors, and first/second signal handling.
internal/conductor Runs timelines: deploy, setup gate, swarm and plan, drive, heal, ending, collect. Also explore (corpus and mutation), replay, shrink (ddmin), causality, and serving workload fault requests.
internal/faults The fault catalog, the seeded planner and mutator, plan validation, the nemesis scheduler, per-kind apply and revert, clock skips through Chaos Mesh, and the heal safety net.
internal/composer The test composer: discovers templates under /opt/antithesis/test/v1/ and schedules the seven command types. Execution is pluggable for tests.
internal/deploy Loads manifests, injects the runtime contract (env, volumes, libvoidstar mounts), installs the in-pod helper scripts, applies, waits for rollout and resets between timelines.
internal/props Ingests SDK JSONL, applies the assertion semantics across timelines, groups failures into expressions, scans source trees for the assertion catalog, and derives coverage features.
internal/report Renders report.md, report.json and the self-contained report.html.
internal/ci Publishes the report to the GitHub job summary or as a Buildkite annotation.
internal/cluster k3d lifecycle, the private kubeconfig, subnet selection, the per-node network helper containers, the privileged synthesis-agent DaemonSet, image import, Chaos Mesh install.
internal/config Loads synthesis.yaml, applies defaults and environment overrides.
internal/events The per-timeline event log (events.jsonl), stamped with time since setup completed.
internal/rng The single source of randomness: one root seed split into named substreams.
internal/sh Runs docker, kubectl and k3d with captured output; fakeable in tests.
internal/fsx Atomic file writes.
internal/log synth’s logger: plain progress lines on stderr, debug detail with SYNTH_VERBOSE.
voidstar/ libvoidstar: the C source (embedded with go:embed), its Docker build and cache, and the smoke test.
conformance/ Fixtures from all seven official SDKs and the test that checks synthesis’ verdicts against them.
examples/kv, examples/pyvoid Example systems under test.
e2e/ The opt-in end-to-end test against a real k3d cluster.

Randomness

Section titled “Randomness”

Every decision comes from internal/rng. The root seed is split into named substreams (swarm, faults, ending, voidstar, per-command seeds, …), so changing how one subsystem consumes randomness does not reshuffle the others. No tool is ever asked to choose a target itself, so plan.json fully describes the nemesis’ decisions.

The cluster

Section titled “The cluster”
  • Nodes get static IPs from cluster.subnet, so a restarted node keeps its address.
  • Traefik and metrics-server are disabled. Kubelet eviction thresholds are lowered to 1% and image garbage collection is disabled, so a full shared disk does not masquerade as chaos and imported images are never evicted.
  • Node failure detection is shortened to about 20 seconds so fault episodes fit a CI budget.
  • Clusters are created with --kubeconfig-switch-context=false, and synth exports its private KUBECONFIG to every tool it runs. Parallel runs never drive each other’s clusters.
  • Node network faults run in a long-lived helper container that shares the node’s network namespace; it is recreated after a node restart. Pod faults run through the privileged synthesis-agent DaemonSet in the synthesis-system namespace, which enters the pod’s namespaces.

One timeline, through the code

Section titled “One timeline, through the code”
Step Where What happens
1 conductor/setup.go Heal leftovers, wait for nodes, remove clock skews, deploy.Reset, create the host output directory, build libvoidstar once, inject, re-import missing images, deploy.Apply.
2 conductor/setup.go Wait for rollout, then for an antithesis_setup line (bounded by signalGrace). Record “Setup completed”; on failure save kubectl get/describe/events/logs under <timeline>/setup-failure/.
3 conductor/timeline.go Discover templates, choose one, run a first_ command without faults.
4 conductor/plan.go List fault targets, draw the swarm, plan or admit the faults, write an early plan.json.
5 conductor/timeline.go Start the nemesis and the fault-request watcher; drive commands for duration.
6 conductor/timeline.go Pick the ending, stop drivers and nemesis, heal pods and nodes, wait quiescence, run eventually_ or finally_.
7 conductor/collect.go Copy pod output, ingest SDK lines, save pod logs, compute default checks, write plan.json and result.json.

Steps up to the plan can fail the timeline with a harness error; a cancel during them marks it interrupted instead (no fault was injected yet). From the drivers on, everything runs to the end, so even an interrupted timeline is healed and collected.

The host–pod trust boundary

Section titled “The host–pod trust boundary”

Everything a pod can write is untrusted: the host output directory is bind-mounted into every pod of your system, and a plan file may come from anywhere. synth treats both accordingly.

  • One accessor. The conductor reaches a timeline’s output directory only through an os.Root, so a symlink planted by a pod cannot lead outside it.
  • Regular files only. Reads open regular files only and never block (a FIFO or device cannot hang or flood the host).
  • Size caps. 64 MiB per copied file (truncated beyond), 1 GiB per timeline copy, 100,000 directory entries and 16 levels of nesting per walk, 1 MiB per request file (fault requests, stop-faults requests).
  • Atomic writes. Files the conductor writes into the shared directory (fault acknowledgements, the seed file) are written to a fresh temporary file and renamed, so they never follow or reuse a file a pod pre-created.
  • Copy, then parse. SDK output is copied into the artifacts first, and ingestion reads the copy.
  • Plans are validated. A plan read from disk (replay, shrink, causality, run --plan, or a corpus) must name catalog kinds, targets that are current nodes or pods of the right type, and finite non-negative times, durations and parameters before it drives Docker or kubectl.
  • Requests are validated. Workload fault requests are checked against faults.enabled, the fault targets and the overlap rules.

The helper scripts in <mount>/bin are mounted read-only into pods.

Artifacts

Section titled “Artifacts”

plan.json is all replay, shrink and causality need; the sibling result.json supplies the original failures. With explore --corpus FILE, the corpus (at most 200 entries, each a plan and its coverage features) is written to FILE.

End-to-end test

Section titled “End-to-end test”

It builds synth, creates a dedicated cluster syn-e2e on subnet 172.41.0.0/16 with its own kubeconfig, runs synth run --seed 1 on examples/kv, checks that the report exists and a planted bug was found, and deletes the cluster. It needs Docker, k3d, kubectl and about 4 GB of free memory. SYNTH_E2E_DURATION (default 60s) sets the driver phase.

Practical notes

Section titled “Practical notes”
  • Parallel clusters. Give each cluster its own name and subnet (SYNTH_CLUSTER, SYNTH_SUBNET, or distinct cluster: blocks). Each default cluster takes a few GB of memory; two at a time is a sensible limit on a laptop.
  • Root-owned files. Pods write into the mount directory as root. synth clean removes it after synth down; plain rm may need sudo.
  • Host load. Fault timing and recovery are real-time. A busy host makes every timeline slower and noisier; check the load average before long runs.
  • Shared clusters. Discovery and targeting only look at the namespaces your manifests put pods in, so two systems can share one cluster.
  • SDK notices. The Go SDK’s “compiled with CGO” self-check line is filtered out. The SDKs emit only the first true and the first false per assertion per process, which the semantics account for.
  • Setup failures save diagnostics under <timeline>/setup-failure/. A run where every timeline hit a harness error reports “Nothing tested”, never “No findings”, and exits 2.

See also Design notes for the prior art and the decisions behind this design.
